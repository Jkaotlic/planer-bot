# Дизайн: «Смены» — Telegram-бот + мини-апп + веб-админка для рабочих смен

- **Дата:** 2026-07-13
- **Статус:** черновик на утверждение
- **Макеты (v3):** https://claude.ai/code/artifact/b90343b4-86c9-499b-8075-e8af570be395

---

## 1. Цель и суть

Инструмент управления рабочими сменами для **одной команды на одной точке**:

- **Работники** живут в **Telegram Mini App**: смотрят свои смены, обмениваются сменами друг с другом, получают мягкие напоминания. Всё основное — в боте.
- **Админы** заполняют график в **веб-админке** (открывается как мини-апп, удобно с Telegram Desktop): пресеты смен, справедливое распределение нагрузки, лента событий.

Ключевые ценности: наглядный «телеграмный» вид, самостоятельный обмен сменами без бюрократии, **справедливое распределение** (чтобы никто не обижался) и **человечные напоминания**.

## 2. Пользователи и роли

| Роль | Где работает | Что делает |
|---|---|---|
| Работник | Mini App (мобильный Telegram) | свои смены, инициирует/принимает обмен, настройки напоминаний |
| Админ | Веб-админка (Telegram Desktop) | заполняет график, пресеты, распределение, видит события |

- Первый админ(ы) поднимается из env `ADMIN_TELEGRAM_IDS`.
- Роль админа — флаг `is_admin` у работника. Админ тоже может быть работником со сменами.
- **Ролей/должностей у работников нет — все взаимозаменяемы** (обмен возможен любой с любым).

## 3. Границы (scope)

**Входит:**
- Один бизнес, одна точка, одна таймзона (без мультитенантности).
- Прямой обмен сменами 1-на-1 (моя смена ↔ твоя), авто-исполнение + уведомление админу.
- Пресеты смен с сокращённой пятницей.
- Панель баланса нагрузки + (v2) авто-распределение «по-честному».
- Мягкие напоминания вечером накануне.

**Не входит (YAGNI сейчас):**
- Мультитенантность / несколько точек.
- Биржа смен (отдал/забрал в пул) — выбран прямой обмен.
- Обязательный апрув обмена админом — обмен авто.
- Учёт зарплаты/табелей, интеграции с 1С и т.п.
- Отдельный браузерный логин с паролем (вход только через Telegram).

## 4. Архитектура

**Вариант A — модульный монолит, один процесс** (осознанно, под Raspberry Pi 4).

```
repo (workspaces)
├── shared/    доменное ядро: типы, zod-схемы, чистая логика (обмен, баланс,
│              пресеты, классификация смен). Без I/O → максимально тестируемо.
├── server/    Hono (HTTP API + раздача статики) + grammY-бот (long-polling) +
│              Drizzle/SQLite + auth (initData→JWT) + планировщик напоминаний.
├── miniapp/   React + Vite + @telegram-apps/* — экраны работника.
└── admin/     React + Vite — сетка графика, пресеты, баланс, события.
```

- На Pi крутится **один Node-процесс** под systemd (авто-рестарт). Hono отдаёт `/api/*`, `/app` (miniapp) и `/admin` (admin build).
- Бот — **long-polling** (не нужно пробрасывать порт за NAT роутера).
- Мини-апп и админка доступны по HTTPS через **KeenDNS** (валидный серт — обязательное условие Telegram).
- Чёткие границы: доменная логика в `shared` не знает про Telegram/HTTP; бот и API — тонкие адаптеры над ней. Единая точка правды для логики обмена/баланса, чтобы inline-кнопки в чате и мини-апп вызывали один и тот же код.

## 5. Технологии

| Слой | Выбор | Причина |
|---|---|---|
| Язык | TypeScript (full-stack) | общие типы бот/веб/бэкенд |
| БД | SQLite (файл) | 1 команда на Pi; бэкап = копия файла |
| ORM | Drizzle + better-sqlite3 | лёгкий, TS-native, хорошо на ARM |
| HTTP | Hono | крохотный, быстрый, современные типы |
| Бот | grammY (long-polling) | живой фреймворк, отличные типы, плагины |
| Фронт | React + Vite | мини-апп и админка |
| Вид мини-аппа | @telegram-apps/sdk + telegram-ui | нативная тема/компоненты Telegram |
| Auth | initData → HMAC → JWT | стандарт, без паролей |
| Валидация initData | @telegram-apps/init-data-node | проверенная либа, не писать HMAC руками |

**SQLite:** режим WAL; всю запись ведёт единственный процесс. Backup — `cron` + `VACUUM INTO`/копия файла.

## 7. Ключевые сценарии

### 7.1 Онбординг и авторизация
1. Админ(ы) — из env `ADMIN_TELEGRAM_IDS` при старте (сидируется `is_admin`).
2. Админ в админке создаёт работника → получает диплинк `t.me/<bot>?start=<invite_token>`.
3. Работник открывает ссылку → бот привязывает `telegram_user_id` к записи, гасит токен.
4. Mini App и админка авторизуются одинаково: фронт отдаёт `initData` → сервер валидирует HMAC (`auth_date` ≤ ~5 мин) → выдаёт **JWT** (access ~1–6 ч; протух → повторная инициализация из `Telegram.WebApp.initData`). Админские `/api/admin/*` — проверка `is_admin` (403 иначе).

### 7.2 Заполнение графика (админ)
- Сетка «работники × дни недели». Клик по ячейке → панель пресетов; **в пятницу подставляются сокращённые** времена автоматически. Есть «своё время».
- «Скопировать прошлую неделю» (v2) — графики часто повторяются.
- Незанятые слоты (Shift без `employee_id`) — сырьё для авто-распределения.

### 7.3 Обмен сменами (прямой 1-на-1)
Инициатор A: выбирает свою смену `from_shift` → выбирает смену коллеги B `to_shift` (+ сообщение) → создаётся `SwapRequest(pending)`. B получает уведомление в чат с inline-кнопками **[Принять] [Отклонить]** (+ «Открыть в приложении»).

**Машина состояний:**
```
pending ──[B принял]──▶ accepted   (в транзакции меняем employee_id смен; AuditLog; уведомить админа)
   ├──[B отклонил]────▶ declined    (уведомить A)
   ├──[A отменил]─────▶ cancelled
   ├──[смена изменена/удалена]──▶ expired (уведомить обе стороны: «неактуально»)
   └──[наступило время смены]───▶ expired
```

**Правила / инварианты:**
- **Перепроверка в момент принятия** (не создания): обе смены существуют, всё ещё на A и B, обе в будущем.
- Приём **атомарен** (транзакция): меняем `from_shift.employee_id ↔ to_shift.employee_id`.
- Приняли одну заявку по смене → **остальные pending-заявки, затрагивающие эти смены, авто-отменяются**.
- **Запрет двойного бронирования**: обмен отклоняется, если у A или B возникают пересекающиеся по времени смены (жёсткое правило).
- Inline-приём в чате и приём в мини-аппе → один и тот же код в `shared`.

### 7.4 Справедливость и распределение
- **Метрика «честности» — поздние смены** (по выбору пользователя). Вес: вечер = 1, ночь = 2 (поздняя = `template.is_late` или конец ≥ 20:00). Цель — ровное распределение поздних смен по людям.
- **Панель «Баланс»** (MVP, только показ): по каждому — часы, ночные, выходные за период; подсветка перегруза + подсказка.
- **«Распределить честно»** (v2, авто-предложение + апрув): прозрачная жадная эвристика. Идёт по незанятым слотам недели, назначает работника с наименьшим текущим счётом «поздних», учитывая занятость (Availability) и запрет двойного бронирования; при равенстве — у кого меньше часов. Возвращает черновик → админ правит → сохраняет. Не чёрный ящик, легко отлаживать. Часы — вторичный критерий (можно поднять до основного по желанию).

### 7.5 Мягкие напоминания
- **Когда:** вечером накануне, ~20:00 по `TEAM_TZ`. Тихие часы соблюдаются (ночью не пишем).
- **Кому:** по умолчанию — утро и ночь (`template.send_reminder`); день/вечер — опционально. Плюс общий `employee.reminders_enabled`.
- **Текст:** тёплый, под тип смены. Утро → «поставь будильник на ~HH:MM» (= начало − `prep_buffer_min`). Ночь → «отдохни днём, продумай дорогу». День/вечер → лёгкий пинг.
- **Планировщик:** тик раз в несколько минут находит смены, у которых подошёл слот, и шлёт. **Получатель вычисляется в момент отправки** → обмен смены автоматически «переносит» напоминание новому владельцу.
- **Идемпотентность:** `ReminderLog(shift_id, kind)` unique — не задваиваем, в т.ч. после перезагрузки хоста. Смена добавлена слишком поздно (слот прошёл) → тихо пропускаем (без ночных сообщений).
- **Управление:** работник включает/выключает и правит `prep_buffer` в мини-аппе (Настройки).

## 8. Экраны

Полные макеты — в артефакте (v3). Кратко:

**Mini App (работник):** «Мои смены» (свои смены + статус заявок), «Предложить обмен» (своя смена → выбор смены коллеги → нативная кнопка Telegram), «Входящая заявка» (наглядный обмен + Принять/Отклонить), чат с мягкими напоминаниями, экран Настроек.

**Админка:** сетка «работники × дни» + панель пресетов (с сокращённой пятницей), кнопки «Добавить смену» и «Распределить честно», правая колонка «Баланс» + «События». Разделы: Расписание, Работники, Журнал.

## 9. Обработка ошибок и edge-cases

- **Обмен:** перепроверка при принятии; авто-отмена «братьев»; устаревшая заявка → `expired` + уведомление; запрет двойного бронирования.
- **Время:** смены через полночь (`end<start`); все расчёты в `TEAM_TZ`.
- **Auth:** протухший `initData` → 401 + повторная инициализация; не-админ на `/api/admin/*` → 403; неизвестный `telegram_user_id` (не привязан) → бот вежливо просит ссылку-приглашение.
- **Напоминания:** идемпотентность через ReminderLog; пропуск прошедших слотов; уважение тихих часов и `reminders_enabled`.
- **Инфраструктура:** long-polling переживает разрывы сети; launchd авто-рестарт (KeepAlive); SQLite WAL + бэкап по cron; проверка, что KeenDNS-URL открывается во встроенном браузере Telegram (риск — сделать первой задачей).

## 10. Тестирование

- **Доменное ядро (`shared`)** — юнит-тесты: логика обмена (все переходы + инварианты), запрет двойного бронирования, расчёт баланса, пятничные пресеты, распределение, классификация смен и выбор текста напоминания. Пишем по TDD.
- **Server/API** — интеграционные тесты (валидация initData, JWT, маршруты обмена/графика, транзакция обмена).
- **Планировщик** — тест на идемпотентность и «получатель в момент отправки» (после обмена).
- **Бот** — критичный флоу приёма обмена по inline-кнопке.

## 11. Деплой (Mac mini + KeenDNS)

> Обновлено (§14.1): таргет — **Mac mini** (macOS), не Pi.

- Node + `launchd`-сервис (KeepAlive = авто-рестарт), Apple Silicon (arm64).
- SQLite-файл локально на Mac mini; бэкап по `launchd`/`cron`.
- KeenDNS даёт публичный HTTPS-домен → мини-апп/админка грузятся в Telegram. URL мини-аппа и меню-кнопка настраиваются в BotFather.
- Конфиг через env: `BOT_TOKEN`, `ADMIN_TELEGRAM_IDS`, `TEAM_TZ`, `PUBLIC_URL`, `JWT_SECRET`.
- Локальная разработка: туннель (cloudflared) для проверки мини-аппа в реальном Telegram.

## 14. Дополнения (2026-07-13, v1.1)

Добавлено после первичной спеки; уточнено 4 решениями.

### 14.1 Деплой → Mac mini + KeenDNS (заменяет Pi в §11)
Хостим на **Mac mini** (Apple Silicon, macOS) — та же машина, где идёт разработка (Node/SQLite/better-sqlite3 уже работают нативно). Сервис под **launchd** (KeepAlive = авто-рестарт) вместо systemd. SQLite-файл локально, бэкап по `launchd`/cron. Публичный HTTPS-домен — через **KeenDNS** (Mac mini за Keenetic-роутером). Раздача мини-аппа/админки и long-polling бота — как раньше.

### 14.2 Категории записей графика
Запись графика (таблица `shifts`, по смыслу «schedule entry») получает **категорию**:
- `shift` — обычная смена (пресет Утро/День/Вечер/Ночь). **По умолчанию.**
- `vacation` — отпуск (многодневный, без времени).
- `business_trip` — командировка (многодневная, без времени).
- `duty` — дежурство (напр. «на Вавилова»), обычно один день, со временем; `location` = место.
- `offsite` — выездное мероприятие, один день; `location`.
- `weekend_work` — работа в выходной, один день, со временем.

**Изменения модели `shifts` (аддитивная миграция Drizzle):**
- `category` (enum-text, default `'shift'`).
- `endDate` (nullable) — для многодневных; `null` = один день (`date`).
- `start`/`end` → **nullable** (у отпуска/командировки времени нет — весь день).
- `location` (nullable) — место.
Плюс доменный enum `EntryCategory` в `@planer/shared`.

**Наглядность:** в гриде админки и в общем расписании каждая категория — свой цвет/иконка; многодневные тянутся полосой по дням.

### 14.3 Решения (подтверждены)
- **Многодневные** (отпуск/командировка) — **одна запись на диапазон** (`date`..`endDate`). Спецтипы — один день.
- **Обмен** — только записи категории `shift`. Отпуск/командировки/спецтипы ставит и двигает админ (не обмениваемы).
- **Баланс** — считаются `shift` + рабочие спецтипы (`duty`/`offsite`/`weekend_work`); `vacation`/`business_trip` = отсутствие, **не считаются**. Сервер фильтрует по категории перед `computeBalance`.
- **Удаление пользователей — мягкое (архив).** Не хард-делит: `employee.isActive=false` (+ `archivedAt`), будущие смены снимаются (`employee_id=null`), прошлые сохраняются, можно восстановить. Заодно закрывает FK-риск (жёсткий delete employee ломал бы FK из shifts/swap_requests).

### 14.4 Общее расписание команды
Новый экран мини-аппа — **«Команда»/«Расписание»**: read-only общий график всех работников на неделю (все видят всех), те же цвета категорий. Данные — `listShiftsInRange` по всем сотрудникам.

### 14.5 Управление пользователями (админка)
Раздел «Работники»: **добавить** (создать + диплинк-приглашение), **архивировать** (мягкое удаление, 14.3), **восстановить**; список активных/архивных.

### 14.6 Влияние на планы
- `@planer/shared`: `EntryCategory` + хелперы `isSwappable(category)`, `countsForBalance(category)`; обработать nullable-времена (у отсутствий нет длительности).
- `@planer/server`: аддитивная миграция (category/endDate/location/nullable-times, `employee.archivedAt`) + репозитории (записи с категорией, `archiveEmployee`/`restoreEmployee`, `listTeamSchedule`).
- Админка/мини-апп: категорийный ввод, цвета, полосы многодневных, экран «Команда», управление пользователями.

## 15. Дополнение (2026-07-14): распределение работ в выходные дни («биржа желающих»)

Отдельная фича (после справедливости/напоминаний/inline). Отдельная «графа» для работы в выходные — не автораспределение по графику, а marketplace желающих.

**Флоу:**
1. Админ вкидывает **вакантные выходные даты** (доступные слоты работы в выходной).
2. Всем работникам — **уведомление**: «доступны такие-то даты».
3. Заинтересованные **записываются** (opt-in, «хочу эти даты»).
4. Админ **распределяет среди записавшихся** — со **справедливостью по истории** (чтобы одним и тем же не доставалось много) + **подсказкой** админу («этот уже был тогда-то — рассмотри другого»).
5. Работник **подтверждает** → даты **фиксируются** + **записываются для учёта часов на оплату** (админ потом заводит часы в расчёт).

**Нужно:** база/история выданных выходных (fairness-леджер) + фиксация подтверждённых для payroll.

**Модель (проектируется):** `VacantWeekendSlot` (дата, статус), `WeekendInterest` (employee ↔ slot, «хочу»), `WeekendAssignment` (employee ↔ slot, confirmed, hours) — источник для payroll-выгрузки. Справедливость — по числу/часам выданных выходных за период.

**Открытые вопросы (уточнить перед сборкой):**
- (а) «выходной» = только Сб/Вс, или любой день, помеченный вакантным?
- (б) связь с существующей категорией `weekend_work` — переиспользуем или отдельная сущность?
- (в) payroll — нужен список подтверждённых (дата+часы на работника) для ручного заведения, или экспорт (CSV/выгрузка)?
- (г) справедливость — по числу выходных или по часам; за какой период (месяц/квартал)?
- (д) подтверждает работник в мини-аппе / по кнопке в боте?
