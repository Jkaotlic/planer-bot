# Ближайшие смены и подробный журнал

**Дата:** 2026-08-07
**Слой:** 1 (сервис) — полный конвейер SDD + TDD.

Две независимые задачи в одной спеке, потому что обе про «на экране не то, что есть на
самом деле»:

1. Вкладка «Мои смены» показывает прошедшие дни и врёт в заголовке.
2. Журнал показывает сырой JSON, а половина действий в него вообще не попадает.

---

## Часть 1. «Мои смены» — только сегодня и дальше

### Что не так сейчас

`/api/my/shifts?from=` отдаёт **всё будущее** от указанной даты (`listUpcomingForEmployee`,
верхней границы нет). Мини-апп передаёт туда понедельник текущей недели — в двух местах,
`App.tsx` при первичной загрузке и в `reloadData`. Отсюда три расхождения:

- в списке лежат уже прошедшие дни недели;
- в списке лежат смены на месяц вперёд, хотя заголовок секции обещает одну неделю
  (`Мои смены · 4–10 августа`);
- сводка `Эта неделя — N смен · X ч` считается по **всему** массиву, то есть по месяцу
  вперёд, и называет это «этой неделей».

Отдельно: «Сегодня»-чип сверяется с `toISODate(new Date())` — локальной датой браузера.
У человека с телефоном в другом часовом поясе он не загорается ни на одной строке.

### Что становится правдой

**Окно.** Мини-апп перестаёт передавать `from` вовсе. Сервер сам берёт сегодняшнюю дату
**в часовом поясе команды** (`config.teamTz`) — это уже реализованный дефолт роута.
Граница дня перестаёт зависеть от того, где физически находится телефон.

**Дата «сегодня» приходит с сервера.** Роут `/api/my/shifts` возвращает
`{ shifts, today }`, где `today` — дата команды. Экран сравнивает с ней, а не с датой
браузера. Это и есть починка «Сегодня»-чипа.

**Группировка по неделям.** Список неограничен вперёд, поэтому режется на секции:

| Позиция | Заголовок секции |
|---|---|
| неделя, в которой лежит `today` | `Эта неделя · 7–10 авг` |
| следующая | `Следующая неделя · 11–17 авг` |
| дальше | `18–24 августа` |

Границы недель — понедельник, как везде в проекте (`mondayOf` из `@planer/shared`).
Диапазон текущей недели начинается с `today`, а не с понедельника: прошедших дней в
секции нет, и заголовок не должен обещать того, чего в ней не лежит.

**Заголовок и сводка.**

- Заголовок секции — `Ближайшие смены` (без диапазона: диапазоны теперь на подсекциях).
- Сводка в `GreetingHero` — `Осталось на этой неделе — 3 смены · 24 ч`, считается строго
  по остатку текущей недели (`today`..воскресенье), только по `category === "shift"`.
- Если на текущей неделе больше ничего — `На этой неделе смен больше нет`. Список ниже
  при этом продолжает показывать следующие недели.
- Если впереди вообще ничего — прежний `Placeholder` «Пока нет смен».

```
Привет, Игорь
Осталось на этой неделе — 2 смены · 18 ч
─────────────────────────────────────────
Ближайшие смены

  Эта неделя · 7–10 авг
  [Чт 7]  09:00–18:00  День     [Сегодня]
  [Пт 8]  09:00–18:00  День     [Обменять]

  Следующая неделя · 11–17 авг
  [Пн 11] 09:00–18:00  Утро     [Обменять]
  [Ср 13] Весь день    Отпуск
```

### Границы модулей

Вся логика разбиения — чистая функция в новом `miniapp/src/lib/upcoming.ts`:

```ts
export interface UpcomingWeek { label: string; shifts: Shift[] }
export function groupUpcomingByWeek(shifts: Shift[], today: string): UpcomingWeek[]
export function remainingThisWeek(shifts: Shift[], today: string): { count: number; hours: number }
```

`MyShiftsScreen` только рисует результат. Ни дат, ни арифметики недель в JSX.

### Что не трогаем

Вкладку **«Команда»**: там недельная сетка, и прошедшие дни в ней несут смысл — видно,
кто уже отработал. Это осознанное решение, а не забытый случай.

### Тесты

`groupUpcomingByWeek` / `remainingThisWeek`:

- смена ровно на `today` попадает в список; вчерашняя — нет;
- `today` = воскресенье → секция «Эта неделя» состоит из одного дня;
- пустой вход → пустой результат (не падает, не выдумывает секций);
- многодневная запись (`endDate` через границу недели) попадает ровно в одну секцию — ту,
  где лежит её `date`;
- `remainingThisWeek` считает только `category === "shift"`: отпуск не добавляет часов;
- смена на 4-й неделе вперёд получает секцию с голым диапазоном, а не «Следующая неделя».

Сервер: `/api/my/shifts` без `from` отдаёт записи от сегодняшней даты в `teamTz` и
возвращает поле `today` с той же датой.

## Часть 2. Журнал: понятный и полный

### Что не так сейчас

- Веб (`admin/src/screens/JournalScreen.tsx`) заканчивает строку события сырым
  `JSON.stringify(event.payload)` в `<code>`.
- Мини-апп (`miniapp/src/screens/admin/AdminJournal.tsx`) не показывает payload вовсе:
  «Изменена запись · Игорь Петров · 5 августа, 14:32» — и всё.
- `TYPE_LABELS`, `formatMoment`, `monthRangeOf` **продублированы** в обоих консолях, а
  два зеркальных `journal-labels.test.ts` стерегут дубль вручную.
- Часть действий в журнал не пишется совсем (перечень ниже).

### Ядро: `shared/src/audit.ts`

```ts
export type AuditType =
  | "entry_created" | "entry_updated" | "entry_deleted"
  | ... ;                                    // единственный список на весь проект

export interface AuditView {
  icon: string;        // одиночный символ/эмодзи
  title: string;       // «Изменена смена»
  lines: string[];     // подробности, по строке на факт
}

export function describeAuditEvent(event: { type: string; payload: unknown }): AuditView;
```

Функция чистая: ни React, ни БД, ни `Date.now()`. `actorName` и время в неё не входят —
это метаданные строки, их рисует консоль.

**Сервер импортирует тип:** `recordAudit(db, type: AuditType, ...)`, а таблица
описателей — `Record<AuditType, Describer>`. Дальше это стережёт компилятор: новый
`recordAudit(db, "...")` без описания даёт красный `tsc`, а не сырой тип на экране.

**Незнакомый тип не прячется.** Строка из старой БД, которой нет в `AuditType`, даёт
`{ icon: "•", title: <сырой тип>, lines: [форматированный JSON] }`. Журнал никогда не
теряет запись — в худшем случае показывает её некрасиво.

**Дубли удаляются:** `TYPE_LABELS` из обоих консолей, оба `journal-labels.test.ts`,
`formatMoment` и `monthRangeOf` переезжают в `shared`.

### Как читается строка

```
✎  Изменена смена                      Игорь Петров · 5 августа, 14:32
   Марк Волков · ср 12 августа
   было:  без времени
   стало: День 09:00–18:00

🔁  Обмен состоялся                     Аня Смирнова · 5 августа, 09:14
   Аня Смирнова отдаёт: пн 11 авг · Утро 09:00–18:00
   Марк Волков отдаёт: ср 13 авг · День 09:00–18:00

📥  Загружен график из CSV              Игорь Петров · 3 августа, 11:20
   482 записи · 21 человек добавлен · 5 переименовано
   1 имя не опознано

⚖  Смены распределены честно           Игорь Петров · 1 августа, 10:05
   4–10 августа · 37 смен расставлено

🔔  Разосланы напоминания на завтра     система · 6 августа, 20:05
   на 7 августа · 12 человек · 1 не дошло
```

Одна и та же функция в обоих консолях: веб рисует строкой с колонками, мини-апп —
карточкой, но текст побайтово тот же.

### Правки существующих payload'ов

Четыре места, где данных физически не хватает на честную фразу. Правки касаются только
**новых** записей; старые строки отрисуются с тем, что в них есть (`работник #24`), —
это честнее, чем достраивать задним числом текущим состоянием базы.

| Событие | Чего не хватает | Что добавляем |
|---|---|---|
| `entry_created` / `entry_updated` / `entry_deleted` | `auditShape` несёт `employeeId` без имени | `employeeName` |
| `employee_updated` | пишется только состояние *после*: после переименования старого имени нет нигде | `{ before, after }` по изменённым полям |
| `reminder_undeliverable` | `employeeId` без имени | `displayName` |
| `template_roles_changed` / `template_rotation_changed` | `templateId` без названия | `templateName` |

### Новые события

**Админские дыры** — сейчас эти действия не оставляют следа вообще:

| Тип | Где пишется | payload |
|---|---|---|
| `employee_created` | `POST /api/admin/employees` | `employeeId`, `displayName` |
| `employee_invite_issued` | `POST /api/admin/employees/:id/invite` | `employeeId`, `displayName`, `regenerated` |
| `birthday_campaign_updated` | `PUT /api/admin/birthdays/:id` | `employeeId`, `displayName`, изменённые поля: `collectUrl`, `messageText` (факт правки, не текст), `scheduledSendOn` |
| `weekend_unassigned` | `POST /api/admin/weekend/assignments/:id/unassign` | `slotId`, `slot`, `employeeId`, `employeeName` |

Роут `/invite` ничего не отправляет — он выпускает ссылку, которую админ копирует руками.
Поэтому событие называется «выдана ссылка-приглашение», а `regenerated` отличает первую
выдачу от перевыпуска (старая ссылка при перевыпуске перестаёт работать — это факт, ради
которого строка в журнале и нужна). **Сам `inviteToken` в журнал не пишется никогда:**
это действующий ключ к учётной записи, а журнал видят все админы.

**Действия работников** — сейчас в журнале видно только финальное «смена назначена», а
кто вызывался и кто отказался, не видно нигде:

| Тип | Где пишется | payload |
|---|---|---|
| `settings_changed` | `PATCH /api/me/settings` | `employeeId`, `displayName`, изменённые: `remindersEnabled`, `preferredName` |
| `weekend_interest` | `POST /api/weekend/slots/:id/interest` | `slotId`, `slot`, `employeeId`, `employeeName` |
| `weekend_offer_confirmed` | `POST /api/weekend/offers/:id/confirm` | то же |
| `weekend_offer_declined` | `POST /api/weekend/offers/:id/decline` | то же |

`settings_changed` — один тип, а не два: маршрут принимает оба поля одним запросом, и
делить одно действие человека на две строки журнала значит врать о том, что он сделал.
Подробности несут строки описания.

**Бот, свёрнуто** — `reminders_dispatched`:

Пишется в конце `runReminderTick` и **только если реально ушло больше нуля**. Тик крутится
каждые пять минут после 20:00, но `hasReminder` дедуплицирует отправку: первый тик пишет
строку, остальные молчат. payload: `{ forDate, sent, considered }`, актор `null`.

Точечные `reminder_undeliverable` остаются как есть: они редкие и требуют действия админа.

**Осознанно не берём:** вход в мини-апп и запрос картинки `/week`. У них нет естественного
«прогона», чтобы свернуть в одну строку, а поштучно они утопят журнал. Отдельная задача,
вместе с ретеншном журнала.

### Полный список типов после работы

24 существующих + 9 новых = 33. Новые: `employee_created`, `employee_invite_issued`,
`birthday_campaign_updated`, `weekend_unassigned`, `settings_changed`, `weekend_interest`,
`weekend_offer_confirmed`, `weekend_offer_declined`, `reminders_dispatched`.

### Тесты

`shared/src/audit.test.ts`:

- на каждый из 33 типов — тест `describeAuditEvent` на payload'е реальной формы
  (формы сняты с живой базы, значения выдуманы);
- незнакомый тип → `title` равен сырому типу, запись не теряется;
- «тощий» legacy-payload (`reminder_undeliverable` без `displayName`) → `работник #24`,
  без `undefined` и без падения;
- `Object.keys(DESCRIBERS)` покрывает весь `AuditType` — опечатка в ключе ловится тестом,
  даже когда компилятор доволен.

Сервер — по тесту на каждое новое `recordAudit`: действие выполнено → в журнале строка
ожидаемого типа с ожидаемым payload'ом. Плюс:

- `runReminderTick` при нуле отправленных **не** пишет `reminders_dispatched`;
- повторный тик в тот же вечер не пишет вторую строку;
- `employee_updated` после переименования несёт и старое, и новое имя.

Консоли: рендер строки журнала показывает `title` и все `lines`; сырого JSON на экране
не остаётся ни в одном из двух.

### Приватность

Репозиторий публичный, страж — `server/src/db/no-real-names.test.ts`. Все примеры в спеке,
в тестах и в моках берутся из уже существующего вымышленного ростера (`Аня Смирнова`,
`Игорь Петров`, `Марк Волков`). Тест прогоняется перед коммитом.

## Порядок работ

1. Часть 1 целиком — она независима и даёт быстрый видимый результат.
2. `shared/src/audit.ts` + перевод обоих консолей на него, без новых событий: журнал
   становится читаемым на том, что уже пишется.
3. Обогащение четырёх существующих payload'ов.
4. Девять новых событий.
