# Уведомления об изменении графика

Дата: 2026-08-03 · слой 1 (сервис) · спека утверждена Антоном

## Зачем

Сегодня правка чужой записи не шлёт человеку **ничего**: ни создание, ни
изменение, ни удаление. Единственное уведомление на этом пути уходит сторонам
обмена, чью заявку правка обнулила. Человек узнаёт, что его смену перенесли,
только если сам откроет мини-апп.

Вечернее напоминание дыру не закрывает: оно уходит один раз, в 20:00 накануне, и
`reminder_log` не даёт послать второе. Правка, сделанная после 20:00 на завтра,
не порождает ни одного сообщения вообще.

Требование Антона дословно: «если у кого-то меняются смены — ему обязательно
должны прилетать уведомления, мол тот-то тебе поменял смену, было то, стало
другое».

## Решения Антона

1. **Четыре события**: поставили смену, сняли смену, сдвинули дату или время,
   поменяли вид записи.
2. **Автор называется по имени** — «Аня поставил(а) тебе смену…». Рода в базе
   нет (есть имя, но не пол), а правит график чаще мужчина, поэтому глагол
   пишется формой `поставил(а)` — той же, что уже принята в боте (`отдал(а)`,
   `отказался(лась)`). Иначе работник получал бы «Антон поставила тебе смену».
3. **Массовая правка — одно сводное письмо на человека**, а не письмо на каждую
   изменённую запись. Импорт августа это 538 записей; поштучно это лавина и
   гарантированный 429.
4. **Тумблер «Напоминания о сменах» на эти письма не влияет** — отдельный канал.
   Выключив шум, человек не отказывался узнавать, что его смену перенесли.
   Отдельного тумблера для этого канала не заводим.

## Допущения (приняты по умолчанию, Антон может отменить)

- **Прошедшие дни не шлём.** Дата записи раньше сегодняшней по `TEAM_TZ` — письма
  нет. Правки задним числом бывают при оформлении больничного, и «тебе поменяли
  позавчерашнюю смену» это шум.
- **Себе не шлём.** Админ, правящий собственную запись, письма не получает.
- **Обмены и работа в выходной не дублируются.** У них свои уведомления, обе
  стороны уже получают текст с деталями; эти пути новый канал не трогает.
- **Правка только заметки, подписи или локации — не событие.** Ни одно из
  четырёх выбранных событий этим не задето.

## Что считается изменением

Значимые поля записи: `employeeId`, `date`, `endDate`, `start`, `end`,
`category`. Всё остальное (заметка, подпись, пресет, локация) на решение «слать
или нет» не влияет.

- **Поставили** — записи у человека не было, появилась.
- **Сняли** — была, исчезла: удалили либо переписали на другого человека.
- **Изменили** — запись та же, но значимые поля разошлись.

Смена владельца порождает **два** события: «сняли» прежнему и «поставили» новому.

## Архитектура

Два модуля, оба чистые и тестируемые по отдельности.

### `server/src/schedule/schedule-diff.ts` — что произошло

```
diffSchedules(before: Shift[], after: Shift[]): Map<employeeId, EmployeeDiff>
EmployeeDiff = { added: Shift[]; removed: Shift[]; changed: { before: Shift; after: Shift }[] }
```

Чистая функция, никакой базы и никакого Telegram. Сравнивает по `id`; запись,
сменившая владельца, попадает в `removed` одному и в `added` другому.

### `server/src/schedule/change-notice.ts` — что сказать и кому

Строители текстов (по образцу `bot/notify.ts`: текст отдельно от отправки, чтобы
обе двери говорили одними словами) плюс два входа:

- `notifyEntryChange(db, bot, { actor, before, after, now })` — одна правка.
- `notifyScheduleChange(db, bot, { actor, diffs, cause, now })` — сводка.

Оба фильтруют по допущениям выше (прошедшие дни, сам себе, нет `telegram_user_id`)
и возвращают `{ delivered, intended }` — та же пара, что уже отдают рассылка
выходного и ДР.

### Как массовые пути получают диф

Не доверяем бухгалтерии каждого сервиса, а снимаем состояние вокруг операции:

```
withScheduleDiff(db, { from, to }, () => работа()) → { result, diffs }
```

Снимок расписания диапазона **до** и **после**, диф — `diffSchedules`. Одна
механика на импорт CSV, «Распределить честно» и «Заполнить неделю», и она не
может разойтись с тем, что реально легло в базу: читает базу, а не отчёт сервиса
о самом себе. Цена — два чтения диапазона (месяц × 28 человек ≈ 600 строк,
better-sqlite3 синхронный).

### «Заполнить неделю» переезжает на bulk-роут

Сейчас это цикл на клиенте: `createEntry` по разу на выбранный день
(`AdminScheduleScreen.tsx`). С точки зрения сервера это N одиночных правок, то
есть N писем на одно нажатие — прямое нарушение решения 3.

Новый `POST /api/admin/entries/bulk`: массив входов, одна транзакция, один диф,
одно письмо на человека. Побочная выгода — атомарность: сегодня из семи запросов
может пройти четыре.

## Доставка

- Письмо уходит **после** коммита транзакции. Упавший Telegram не откатывает
  правку графика.
- `telegram_user_id IS NULL` — пропускаем, как везде, но **не молча**: роут
  возвращает `notified: { delivered, intended }`, обе админки показывают это по
  правилу `reachNotice` (`c1d03cd`). Для одиночной правки — строкой
  «уведомление не дошло: телеграм не привязан».
- Отказ отправки логируется через `safeErrorMessage` и не роняет ответ роута.

## Тексты

Обращение — через `addressOf`, как во всех остальных сообщениях.

Одиночные:

- `Аня поставил(а) тебе смену: Пт 7 авг, 15:00–23:00 (Вечер).`
- `Аня снял(а) с тебя смену: Ср 5 авг, 08:00–17:00 (Утро).`
- `Аня изменил(а) твою смену: было Ср 5 авг, 08:00–17:00 (Утро) → стало Пт 7 авг, 15:00–23:00 (Вечер).`

Сводное (причина названа — файл, распределение, заполнение недели):

```
Аня обновил(а) твой график (загрузка файла): +3 смены, −1, изменено 2.
• Пн 1 сен, 08:00–17:00 (Утро)
• Вт 2 сен, 15:00–23:00 (Вечер)
…
```

Список обрезается на десяти строках, дальше — «…и ещё N». Одна запись в дифе —
сводки нет, уходит одиночный текст.

## Тесты

- `schedule-diff` — чистые юниты: добавили, сняли, изменили, сменили владельца,
  запись вне диапазона, запись без сотрудника.
- Роуты записей — `fakeBot`: кто получил, что написано, «было → стало».
- Допущения: прошедший день молчит, себе не шлём, непривязанный считается в
  `intended`, но не в `delivered`.
- Массовые пути: импорт месяца шлёт **ровно одно** письмо на человека, а не по
  письму на запись; «Заполнить неделю» из семи дней — одно письмо.
- Отказ Telegram не откатывает правку и не роняет роут.

## Чего сознательно не делаем

- Не копим и не склеиваем письма по таймеру. Админ, правящий три записи подряд
  руками, получит три письма — честно и без таймеров в проде.
- Не заводим второй тумблер (решение Антона).
- Не трогаем уведомления обменов и выходных.
- Не пишем в `audit_log` факт отправки: события `entry_created` / `entry_updated`
  / `entry_deleted` там уже есть, и второй слой записей о том же ничего не
  добавляет.
