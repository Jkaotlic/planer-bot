# Бессмысленный обмен и пустой журнал — дизайн

**Дата:** 2026-07-29
**Статус:** дизайн утверждён пользователем.

## 1. Цель

Две независимые правки:

1. **Обмен, который ничего не меняет.** Двое работают «Утро 5 августа». Один предлагает другому обмен, тот принимает — и у обоих остаётся ровно то же самое. Система это разрешает.
2. **Журнал обещает больше, чем показывает.** В интерфейсе есть подпись «Обмен состоялся», но событие `swap_accepted` не записывается никогда. Так же не пишутся выходные, архивация людей и выдача прав. Фильтровать историю по человеку нельзя — только по типу и датам.

Схема не меняется, миграций нет.

## 2. Обмен одинаковыми сменами

### 2.1 Правило

Новая причина отказа `identical-shift` в `validateSwap` ([`shared/src/swap.ts`](../../../shared/src/swap.ts)), рядом с существующими проверками владения, прошлого и двойного букинга.

Обмен отклоняется, когда **дата совпадает И вид смены совпадает**.

«Вид совпадает» определяется так:

- если хотя бы у одной смены есть `templateId` — виды равны тогда и только тогда, когда `templateId` равны;
- если обе смены без пресета (созданы руками) — виды равны, когда совпали `category`, `start` и `end`.

Первая ветка важнее второй: пресет и есть идентичность смены в этом проекте, а два разных пресета могут случайно совпасть по времени.

### 2.2 Что осознанно НЕ запрещается

«Утро 5 августа» ↔ «Утро 12 августа» остаётся разрешённым. Это обмен днями внутри одного вида смены — ровно то, ради чего обмены и нужны: человеку нужен свободный вторник, он отдаёт свой вторник и берёт чужую пятницу. Запрет по одному лишь совпадению вида убил бы главный сценарий.

Обмен внутри одного дня между разными видами («Утро» ↔ «Ночь» пятого числа) тоже остаётся: он меняет обоим время работы.

### 2.3 Где ставится заслон

**На клиенте** — такие смены не попадают в список кандидатов ([`App.tsx`](../../../miniapp/src/App.tsx), где собирается `colleagueShifts`). Не предложить лучше, чем отказать после выбора.

**На сервере** — `validateSwap` отклоняет. Клиентский фильтр не является защитой: список приходит из данных, которые могли устареть между загрузкой и тапом.

### 2.4 Сопутствующая дыра, которую надо закрыть

Отказ сервера при предложении обмена сейчас никем не ловится:

- `handleConfirmSwap` в `App.tsx` не имеет `catch`;
- `handleConfirm` в [`ProposeSwapScreen.tsx`](../../../miniapp/src/screens/ProposeSwapScreen.tsx) имеет `try/finally` без `catch`.

Любой отказ — не только новый — улетает в необработанный промис, а пользователь видит кнопку, которая перестала нажиматься. Мы добавляем причину, в которую люди будут упираться регулярно, поэтому ошибка должна показываться на экране текстом.

## 3. Журнал

### 3.1 Записывать то, что потеряно

Восемь типов событий. `audit_log` уже хранит `type`, `actorEmployeeId`, `payload`, `createdAt` — ничего нового не нужно.

| Тип | Когда | Актор |
|---|---|---|
| `swap_proposed` | работник предложил обмен | инициатор |
| `swap_accepted` | обмен принят, смены поменялись | принявший |
| `swap_declined` | обмен отклонён | отклонивший |
| `swap_cancelled` | инициатор отозвал заявку | инициатор |
| `employee_archived` | работник убран из ростера | админ |
| `employee_restored` | работник возвращён | админ |
| `employee_admin_changed` | выданы или сняты права админа | админ |
| `weekend_slot_created` | открыта выходная смена | админ |
| `weekend_assigned` | выходная смена назначена человеку | админ |

Переключение напоминаний намеренно не пишется: это личная настройка работника, шума от неё больше, чем пользы.

**Правило для payload:** строка журнала должна читаться без join'ов. Существующие события кладут в payload человекочитаемые имена — новые делают так же. Например, `swap_accepted` несёт имена обеих сторон и обе смены строкой, а не одни идентификаторы.

**Запись аудита никогда не роняет действие.** `recordAudit` уже глотает свои ошибки — это свойство сохраняется: обмен состоялся, даже если журнал не записался.

### 3.2 Фильтр по человеку

- `AuditQuery` получает необязательное поле `actorEmployeeId`.
- `GET /api/admin/journal` принимает `?actor=<id>`; нечисловое значение — `400`.
- Ответ получает `availableActors: { id: number; displayName: string }[]` рядом с уже существующим `availableTypes` — фильтр предлагает только тех, кто действительно что-то делал. Список строится из `audit_log`, а не из ростера.
- События без актора (тик бота пишет `null`) под фильтр по человеку не попадают — это верно: у них нет автора.

### 3.3 Интерфейс

В [`AdminJournal.tsx`](../../../miniapp/src/screens/admin/AdminJournal.tsx), вкладка «Кто менял»: выбор человека рядом с существующим выбором типа. Пустой выбор — все.

`TYPE_LABELS` пополняется подписями для девяти новых типов, иначе они покажутся сырыми кодами. Подписи короткие, в том же стиле, что и существующие («Обмен состоялся», «Изменена запись»).

## 4. Тестирование

| Что | Где | Проверяет |
|---|---|---|
| Правило одинаковой смены | `shared/src/swap-validate.test.ts` | тот же день + тот же пресет отклоняется; тот же пресет в другой день проходит; разные пресеты в один день проходят; смены без пресета сравниваются по времени |
| Отказ на сервере | `server/src/http/swaps.test.ts` | `POST /api/swaps` отвечает 400 с `identical-shift` |
| Записи аудита | `server/src/http/swaps.test.ts`, `employees.test.ts`, `weekend.test.ts` | каждое из девяти событий появляется в журнале с нужным актором |
| Фильтр по человеку | `server/src/http/journal-route.test.ts` | `?actor=` сужает выдачу; `availableActors` содержит только реальных; события без актора не попадают |

Логика правила — чистая функция, тестируется без БД. Интерфейс проверяется typecheck'ом и неполоманным набором; при желании — `renderToStaticMarkup` без jsdom, как уже принято в проекте.
