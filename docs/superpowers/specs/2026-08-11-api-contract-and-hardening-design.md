# Контракт API, границы пакетов и укрепление эксплуатации

**Дата:** 2026-08-11
**Слой:** трек A — 1 (сервис) и 2 (UI), полный конвейер SDD + TDD. Треки B и C — 3
(инфра-скрипт): постусловия вместо тестов.

Его заявка от 2026-08-11: «посмотри на проект свежим взглядом и предложи улучшения по
всем параметрам» → одиннадцать пунктов аудита → «делаем все».

Одиннадцать пунктов — это не одна работа. Они распадаются на три трека, и только один
из них требует спеки. Этот документ описывает все три, потому что порядок между ними
важен, но подробно расписан трек A; B и C зафиксированы как постусловия, как и положено
слою 3.

---

## Порядок треков и почему именно такой

**C (гигиена) → B (эксплуатация) → A (контракт).**

Не по важности, а по зависимостям:

- **C идёт первым**, потому что линтер и обновлённые инструменты должны стоять *до*
  большого рефакторинга. Иначе весь трек A пишется без `no-floating-promises` — в коде,
  где промисы осознанно запускаются через `void` (`server/src/index.ts:24`), — и на
  vitest 2, отставшем на два мажора.
- **B идёт вторым**, потому что логи полезно иметь *до* выкладки рефакторинга, а не
  после. Трек A трогает все 61 маршрут; если что-то поедет в проде, узнать об этом
  сейчас неоткуда — на весь сервер два `console.error`
  (`server/src/util/ticks.ts:31`, `server/src/http/app.ts:184`).
- **A идёт последним** и занимает больше времени, чем оба предыдущих вместе.

## Трек A. Контракт API и границы пакетов

### Что сегодня неправда

1. **Контракт API не записан ни в одном месте.** Сервер собирает ответы руками
   (`c.json({ ... })` в 61 маршруте `server/src/http/app.ts`), а два клиента —
   `admin/src/api/client.ts` (998 строк) и `miniapp/src/api/client.ts` (1164) — руками
   же их типизируют. Между этими тремя описаниями нет ни одной проверки: ни компилятор,
   ни тесты не заметят, если сервер перестанет отдавать поле, которое клиент ждёт.

2. **Расхождение уже произошло.** Одноимённые типы в двух клиентах разные:

   | Тип | В мини-аппе есть | В админке нет |
   | --- | --- | --- |
   | `Employee` | `preferredName` | — |
   | `Shift` | `location`, `employeeName` | — |
   | `Template` | `sortOrder` | — |

   Плюс один и тот же тип называется `Category` в мини-аппе и `EntryCategory` в админке.

   Это не «риск разойтись» — это уже разошлось, молча, и обнаружено только чтением двух
   файлов рядом.

3. **Логика клиента живёт в двух копиях.** Разбор ошибок, `OFFLINE_MESSAGE`, работа с
   токеном, повторы — всё дважды. Dev-моки — тоже дважды: `admin/src/api/mock.ts` (1077
   строк) и `miniapp/src/api/mock.ts` (1466).

4. **`app.ts` — 1775 строк на 61 маршрут.** Маршруты сгруппированы по темам визуально,
   но ничем, кроме порядка строк, эта группировка не закреплена.

5. **Dev-моки спят по-настоящему.** `await delay(200..350)` внутри мока — и
   `miniapp/src/api/mock.test.ts` становится самым медленным файлом проекта: 13.5 с на 19
   тестов, плюс 4 с на 5 тестов в `admin/src/api/mock.test.ts`.

### Решения, которые он принял (2026-08-11)

Записаны как решения, а не как выводы: код их не объясняет.

1. **Обе админки остаются.** Браузерная консоль и админский раздел мини-аппа продолжают
   существовать обе. Общим становится слой данных, а не UI. Экраны по-прежнему пишутся
   дважды — это принято сознательно.
2. **Контракт закрепляется zod-схемами в `shared`, проверяются они в тестах.** Сервер
   типизирует ответы через `satisfies` (расхождение → ошибка компиляции), тесты ручек
   прогоняют настоящий ответ через схему (расхождение → красный гейт). В проде схемы не
   исполняются: этот процесс обслуживает и API, и long-poll бота, и платить процессором
   за валидацию каждого ответа он не будет.
3. **Один общий dev-мок вместо двух.** Разработка фронта без поднятого сервера
   сохраняется; задержка становится параметром и равна нулю в тестах.
4. **Пять воркспейсов вместо четырёх.** Контракт — в `shared`, транспорт — в новом
   `client/`.

### Границы пакетов

```text
shared/          доменные правила (как сейчас)
                 + shared/src/api/ — zod-схемы контракта
   ↑                                    ↑
server/                            client/  (@planer/client)
                                   ApiClient, dev-мок, разбор ошибок
                                        ↑
                                 miniapp/     admin/
```

Граница проведена по одному признаку: **контракт — общее знание сервера и клиентов,
транспорт — знание только клиентов.** Поэтому zod-схемы уезжают в `shared` (который уже
зависит от zod и уже общий для всех), а `ApiClient` с его `fetch`, `localStorage` и
`import.meta.env` — в отдельный пакет, которого сервер не видит.

Два правила, которые эту границу держат:

- `server/` не импортирует `@planer/client`;
- `shared/` не упоминает `fetch`, `localStorage`, `window`, `document`, `import.meta`.

Оба проверяются тестом. Без теста граница продержится до первого удобного импорта — это
не пессимизм, а наблюдение: ровно так `Category` и `EntryCategory` стали двумя именами
одного типа.

### Устройство `shared/src/api/`

По файлу на домен, в каждом — zod-схемы ответов и типы через `z.infer`:

```ts
// shared/src/api/employees.ts
export const employeeSchema = z.object({
  id: z.number().int(),
  displayName: z.string(),
  preferredName: z.string().nullable(),
  // …
});
export type Employee = z.infer<typeof employeeSchema>;

export const employeesResponseSchema = z.object({ employees: z.array(employeeSchema) });
export type EmployeesResponse = z.infer<typeof employeesResponseSchema>;
```

Сервер:

```ts
return c.json({ employees: listEmployees(db) } satisfies EmployeesResponse);
```

Тест ручки — новый вид теста, контрактный:

```ts
const res = await app.request("/api/employees", { headers: auth(token) });
expect(employeesResponseSchema.safeParse(await res.json()).success).toBe(true);
```

Здесь важна деталь, иначе тест окажется из тех, что не могут упасть: `z.object` по
умолчанию **отбрасывает** лишние поля и проходит. Проверка «сервер отдал ровно
обещанное, без лишнего» требует `.strict()` на схемах ответов. Лишнее поле в ответе —
это не косметика: это поле, которое кто-то начнёт читать, не найдя его в контракте.

### Устройство `client/`

Один `ApiClient` на оба фронта. Фронты отличаются ровно одним — где взять токен:

```ts
export interface TokenSource {
  /** Действующий токен; бросает AuthRequiredError, если войти нельзя. */
  get(): Promise<string>;
  /** Сбросить кэш — вызывается на 401. */
  clear(): void;
}
```

Мини-апп реализует его через Telegram `initData`, админка — через `#token=` из ссылки
бота (`server/src/bot/bot.ts:298`) с хранением в `localStorage`. Всё остальное — путь
запроса, разбор ошибок, `OFFLINE_MESSAGE`, повтор после 401 — общее и в одном месте.

Dev-мок переезжает туда же. Задержка становится параметром конструктора: реалистичные
200–350 мс в `npm run dev`, ноль в тестах.

### Один срез

Работа идёт вертикальными срезами по доменам. Срез — это домен целиком:

1. Инвентаризация расхождений домена (см. ниже) и решения по ним.
2. Zod-схемы домена в `shared/src/api/`.
3. Маршруты домена вынесены из `app.ts` в свой роутер, подключены через `app.route()`.
4. Ответы сервера типизированы через `satisfies`.
5. Контрактные тесты ручек домена.
6. Методы домена переехали в `client/`, мок домена — туда же.
7. Оба фронта переведены на общий клиент в части этого домена.

Гейт зелёный после каждого среза. Состояние «половина переехала» не живёт дольше одной
задачи.

### Порядок доменов

`read` → `employees` → `entries` → `swaps` → `weekend` → `collections` → `roster` →
`reports` → `auth/me`.

Первым идёт `read` (`/api/templates`, `/api/my/shifts`, `/api/team/schedule`) — он
маленький, и на нём обкатывается форма среза. Если форма окажется неудачной,
переделывать придётся один домен, а не девять.

`auth/me` идёт последним намеренно: он трогает вход в оба приложения, и ломать его
стоит тогда, когда каркас уже обкатан на восьми доменах.

`app.ts` в конце — не пустой файл, а сборка: middleware, `onError`, `/api/health` и
девять `app.route()`. Порядка полутора сотен строк.

### Расхождения: как решаются

Перед каждым срезом — инвентаризация: все поля, где типы двух клиентов разошлись, с
рекомендацией по каждому. Разбираются по его правилу о находках:

- **Чисто типовое** (`Category` против `EntryCategory`, недостающее поле, которое
  админка просто не описала и нигде не читает) — чиню сам, план правлю, ему сообщаю
  строкой.
- **Меняет поведение на экране** — несу ему, не решаю сам.

Уже известный случай второго рода, найденный при брейншторме:

> Обе админки кладут место дежурства в `title`
> (`admin/src/components/AddEntryPanel.tsx:121`,
> `miniapp/src/screens/admin/AdminScheduleScreen.tsx:621`), сервер сохраняет присланное и
> сам `location` из пресета не выводит (`server/src/http/app.ts:961`), а
> `miniapp/src/screens/team/TeamEntryDetails.tsx:19` показывает «Место: …» именно из
> `location`. Похоже, для записей, созданных через админку, эта строка не показывается
> никогда.

Проверено не полностью: остальные пути записи (CSV-импорт, выходные) не прочитаны. Это
**не входит в трек A** — чинить поведение заодно с рефакторингом значит смешать две
работы и лишить обе доказательства. Находка передаётся в `/goal` (линза `ui` или
`mirrors`) и живёт в `docs/audit/ledger.md`. Трек A обязан лишь не закрепить молча одну
из двух версий: в схеме `location` описывается как есть, поведение не меняется.

### Что в трек A не входит (YAGNI)

- **Общие компоненты UI.** Экраны остаются в двух копиях — решение владельца.
- **Генерация клиента из OpenAPI.** Схемы пишутся руками. Генератор — это ещё один
  инструмент в сборке ради контракта, который и так проверяется компилятором и гейтом.
- **Рантайм-валидация ответов в проде.** Решение 2.
- **Починка `location`.** Отдельная работа, см. выше.
- **Версионирование API.** Один сервер, два клиента, выкладываются вместе.

## Трек B. Эксплуатация

Слой 3 — постусловия вместо тестов.

**Что должно стать правдой:**

1. `ops/com.planerbot.server.plist` лежит в репозитории — с плейсхолдерами вместо путей
   и секретов. Сегодня плист бэкапа в `ops/`, плист меню-бара в `mac/`, а плист самого
   сервиса, на который ссылаются `README.md:315` и `mac/PlanerBotMenu.swift:249`,
   существует только на машине.
2. Сервер пишет структурный лог: старт и остановка, каждый неуспешный запрос, каждый
   отправленный ботом текст, результат каждого тика. Один хелпер `log(event, fields)`
   вместо голых `console.*`; вывод — в файл через `StandardOutPath` / `StandardErrorPath`
   в плисте, с ротацией через `newsyslog.d`.
3. Здоровье сервиса проверяется без участия человека: задача launchd раз в 5 минут
   опрашивает `/api/health`; после N неудач подряд делает `kickstart` и пишет владельцу в
   Telegram.

**Проверка постусловий:** плист применён на живой машине и сервис поднялся под ним
(`launchctl print`); в логе после рестарта видны строки старта; health-задача, натравленная
на заведомо мёртвый порт, действительно прислала сообщение.

Порог N и адрес получателя алерта — решаются в начале трека B, не сейчас.

## Трек C. Гигиена

Слой 3 — постусловия вместо тестов.

**Что должно стать правдой:**

1. `npm audit` без high-уязвимостей в рантайм-зависимостях (`--omit=dev`). Сегодня их 7
   (2 moderate, 5 high), и рантайм-часть — это ровно три пакета:

   | Пакет | Сейчас | Куда | Что чинит |
   | --- | --- | --- | --- |
   | `hono` | 4.12.30 | 4.13.1 | четыре CVE, включая ReDoS в CORS |
   | `@hono/node-server` | 2.0.8 | 2.1.0 | DoS через оборванный WS-handshake |
   | `@telegram-apps/sdk-react` | 3.3.9 | 3.11.8 | ReDoS в `valibot` (high) |

   **Ловушка, зафиксированная явно:** `npm audit fix --force` для valibot предлагает
   `@telegram-apps/sdk-react@2.0.25` — то есть **даунгрейд на мажор назад**. Правильный
   путь противоположный: вверх до 3.11.8 внутри того же мажора, где valibot уже 1.4.2 с
   фиксом. `--force` в этом треке не запускается вообще.

   Мажоры инструментов (`vitest` 2 → 4, `vite` 6 → 8) **в постусловие не входят**: они
   dev-only, а их уязвимость — известный esbuild-CVE про dev-сервер. Делаются отдельным
   шагом после остальных, с зелёным гейтом после каждого; если ломаются — откатываются
   без ущерба для постусловия. Мажор `react` 18 → 19 не делается в этой работе вовсе.
2. `.github/dependabot.yml` есть — чтобы следующий разговор про уязвимости завёл робот, а
   не аудит через полгода.
3. Линтер стоит и гоняется в CI. Biome: один конфиг, секунды на прогон. Обязательные
   правила — `no-floating-promises` и `no-unused-vars`.
4. `README.md` не обещает Node.js 20: `package.json` требует `>=22.22.2`, и комментарий в
   `.github/workflows/ci.yml` объясняет, почему на двадцатке молча отваливались все
   экранные тесты. Сегодня README обещает 20 и в бейдже, и в требованиях.
5. `CLAUDE.md` и зеркальный `AGENTS.md` в корне: какой слой у какого каталога
   (`server/`, `shared/`, `miniapp/`, `admin/` — 1–2; `mac/`, `ops/`, плисты, CI — 3),
   как гонять гейт, правило про настоящие ФИО, правило про русские комментарии.
6. Ветки `feature/custom-collections` и `feature/duty-swaps` удалены: обе вмержены,
   уникальных коммитов ноль.

**Проверка постусловий:** `npm audit` и `npm test` показаны с выводом; линтер прогнан по
всему дереву; `git branch` показывает отсутствие удалённых веток.

## Риски

1. **Трек A — это порядка 15 задач.** Соблазн срезать угол будет на седьмом домене, а не
   на первом. Защита — форма среза, одинаковая для всех девяти, и зелёный гейт после
   каждого.
2. **Инвентаризация расхождений может вскрыть больше, чем один `location`.** Это не повод
   расширять трек A: каждая находка про поведение уходит в ledger, а не в эту работу.
3. **Пятый воркспейс — новая точка сборки.** Оба фронта собираются через `vite`, и
   `@planer/client` должен собираться так же прозрачно, как `@planer/shared` сегодня.
   Проверяется на первом же срезе: `npm run build` обоих фронтов входит в определение
   готовности каркаса.
4. **Мок остаётся рукописным.** Общие zod-схемы пристёгивают его к контракту по форме, но
   не по поведению: мок по-прежнему может отвечать правдоподобно и неверно. Это цена
   решения 3, принятая сознательно.
